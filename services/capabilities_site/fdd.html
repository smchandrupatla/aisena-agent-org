AISENA — Domain-Agnostic AI Agent Organization

Complete functional definition of what AISENA is, what it does in the true sense, how the multi-agent operating model works, and why it exists as a reusable delivery system for any business domain.

1. Executive Summary & Mission

AISENA is a domain-agnostic AI implementation system for building software delivery organizations, product teams, and end-to-end implementation workflows across any business vertical.

It is not a single-product chatbot. It is a staffed, tooled, governed AI agent organisation that turns sponsor goals into planned, coded, tested, documented, and releasable software with minimal hand-holding.

Same architecture applies to compliance, healthcare, logistics, retail, SaaS, internal tooling, risk and fraud. Repo examples are demonstrations — not constraints.

2. What AISENA Is (True Sense)

An autonomous delivery shop: specialised AI agents collaborate via versioned artifacts, handoff protocols, and orchestration. The sponsor talks mainly to the Implementation Manager.

Not

  • Generic multi-agent chat without delivery discipline
  • Locked to one vertical
  • A black-box that silently changes production
  • A replacement for human accountability on legal, financial, or production decisions

Does

  • Translates goals into requirements, architecture, and buildable increments
  • Runs definition, engineering, platform, assurance, and completion in parallel where contracts allow
  • Produces runnable, testable artifacts every stage
  • Maintains append-only logs, handoffs, and status reports
  • Exposes a web portal for dashboards, tasks, issues, agent chat, and ops viewers

3. Value Proposition & Marketing

6. Architecture (Stage 0 proof)

Sample Event → Stage0 Ingestor → Kafka (aisena-stage0-events)
    → Screening Service → OpenSearch (aisena-stage0-screening-results)
    → Validation

Broader stack: Kafka, ingestion/detection/agent-manager/API/orchestrator, PostgreSQL, OpenSearch, capabilities site, Prometheus/Grafana/Loki, Redmine, Vault, Apicurio.

7. Staged Roadmap

Stage 0 Team pipeline proof — full handoff chain + toy screening flow
Stage 1 Ingestion + search — parser → Kafka → OpenSearch on Minikube
Stage 2 Stubbed screening — sanctions/fraud detection services
Stage 3 Case management — alert-to-case, disposition, audit trail
Stage 4 Security hardening — auth, secrets, compliance controls
Stage 5 Cloud portability — EKS / MSK / OpenSearch Service

8. Web Portal

Primary surface: services/capabilities_site. Nav includes Overview, Capabilities, Wiki, FDD, Create New App, Tasks, Issues, dashboards, Postgres/Kafka/Splunk/Dynatrace viewers, Agent Learning, Workflow, Guardrails, Agents + Chat, Documentation.

9. Governance & Guardrails

Human approval is mandatory before actions that touch production, real infrastructure spend, user-data handling, pricing, or legal/regulatory exposure. CI runs on every push/PR (unit tests, feature-health, Selenium screens, schema and compose validation).
