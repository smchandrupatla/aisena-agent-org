From a plain-language goal to an independently deployable app.

The same staged approach applies regardless of domain or application type. Start any new build from the Create New App intake wizard; the stages below describe what happens after you submit it.

Delivery stages

  1. Stage 0
    Intake and framing Domain Analyst and Business Analyst turn the intake form into actors, workflows, entities, and testable acceptance criteria. Product Owner sequences the initial backlog.
  2. Stage 1
    Architecture and design Solution Architect defines service boundaries, data flow, and integration contracts. Implementation Pattern Specialist selects reusable patterns instead of one-off designs. UI/UX Designer (and Case Management UX SME, where relevant) map the user journeys.
  3. Stage 2
    Portal and environment setup Infrastructure/Platform Engineer and DevOps Engineer stand up an independently deployable portal and environment for the new application — kept separate from the AISENA framework portal, with its own routes, configuration, and branding.
  4. Stage 3
    Engineering build-out Frontend, Backend, Database, Integration, and Mobile App Engineers implement the approved design in small, testable increments, each ending in a working slice rather than a big-bang delivery.
  5. Stage 4
    Validation QA Engineer, Test Automation Engineer, Performance Engineer, and Security Engineer verify functionality, regression safety, load behavior, and vulnerability posture with recorded evidence, not narrative claims.
  6. Stage 5
    Release and operate Release Manager and DevOps/Release Engineer coordinate go-live with a rollback plan; Documentation/Technical Writer produce runbooks and handoff material for ongoing operation.

Portal isolation is non-negotiable

Every new application gets its own web portal: its own source boundary, configuration, routes, assets, and branding, versioned and releasable independently. Shared libraries and platform services may be reused, but the AISENA portal itself is never extended with application-specific screens or navigation.

Deployment targets

The intake wizard captures whether the new app runs local-only (Docker Compose / on-prem), cloud-only (AWS, GCP, Azure, managed PaaS), or hybrid (local proof with a cloud production path). The same agent roster plans and builds for any of the three.

Handoffs, not hallways

Each stage transition produces a written handoff file (project/handoffs/TASK-NNNN-FROM-role-to-ROLE.md) covering the objective, files changed, decisions made, next actions, and open blockers, so any role can resume the work.

Approval gates stay in force

Autonomous engineering continues throughout, but production go-live, real infrastructure/API spend, user-data handling changes, pricing changes, or legally exposed decisions always route to a human approver before proceeding.

What each stage produces

Stage Primary roles Artifacts
Intake and framing Domain Analyst, Business Analyst, Product Owner Requirements, user stories, acceptance criteria, initial backlog
Architecture and design Solution Architect, Implementation Pattern Specialist, UI/UX Designer Architecture decisions (ADRs), interface contracts, UX flows
Portal and environment setup Infrastructure/Platform Engineer, DevOps Engineer New portal scaffold, environment config, CI/CD pipeline skeleton
Engineering build-out Frontend, Backend, Database, Integration, Mobile App Engineers Working code increments, tests, API and schema definitions
Validation QA, Test Automation, Performance, Security Engineers Test evidence, scan reports, load results, defect logs
Release and operate Release Manager, DevOps/Release Engineer, Technical Writer Release notes, rollback plan, runbooks, change log entries
