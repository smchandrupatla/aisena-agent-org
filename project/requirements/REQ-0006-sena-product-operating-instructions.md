# REQ-0006 — Sena Product Operating Instructions

Status: ACCEPTED
Date: 2026-08-20
Owner: Product Owner / Client Input

## Purpose
Sena is an autonomous AI dev shop that sits beside each application it builds, taking direct feature requests and proposing its own improvements, while guaranteeing the application stays production-ready at every step. This requirement codifies the operating instructions Sena must follow for every application it builds or evolves.

## Source Requirement
Product Owner / Client "AI Sena — Operating Instructions" mandate provided on 2026-08-20.

## In Scope
- Workspace and repository separation between Sena and each application it builds.
- Intake of both direct product-owner instructions and Sena's own self-initiated improvement proposals.
- A mandatory, no-exceptions change pipeline from implementation through human go-ahead.
- Append-only audit trail: running changelog, living architecture document, rollback plan per change.
- Visible-in-GUI requirement for every change, with a plain-language change summary.
- Configuration-driven design philosophy with a runtime web configuration console.
- Self-service diagnostics and operator remediation actions.
- Enterprise-grade non-functional requirements (resilience, observability, logging, RBAC, performance monitoring, upgrade safety, multi-tenant isolation).
- Continuous security and standards-compliance scanning.

## Out of Scope
- Continuous/automated deployment to production (CI only, never CD).
- Mixing Sena's implementation-manager schema/state with an application's own database schema.
- Silent or automatic implementation of self-initiated improvements without explicit approval.

## Functional Requirements

### 1. Workspace & Repository Structure
- Sena lives in a sibling directory next to the application codebase — never mixed into it; logical separation is mandatory at all times.
- Sena has read/write access to application code for the purpose of implementing changes.
- Sena's implementation-manager database schema is always separate from the application's own database schema — no shared schema, ever.
- On request, Sena can generate a clean new repository containing only the application code, with Sena fully removed and all dependencies resolved, ready to build and deploy independently. Extraction must be repeatable on demand at any point in the project.

### 2. Sources of Work
- Direct instructions from the product owner (feature requests, fixes, changes).
- Self-initiated improvement proposals generated by Sena reviewing the codebase and industry standards.
- Self-initiated changes always require explicit approval before implementation begins — never automatic, never silent.

### 3. Change Pipeline (No Exceptions)
Every change, regardless of source, must pass through:
1. Implementation.
2. Full test suite.
3. Regression testing.
4. Marked "ready" only after passing all tests.
5. Final human go-ahead before touching the live application.
- No automated deployment — continuous integration only, never continuous deployment.
- The application must be production-ready after every single change, not just at release milestones.
- Every change is tagged with a risk level: Low / Medium / High. Medium and High risk changes always require explicit human review regardless of test results.

### 4. Transparency & Audit Trail
- Sena maintains a running changelog capturing every change (requested or self-initiated) and the reasoning behind it.
- Sena maintains a living architecture document for the application, kept current as features are added.
- Every change includes a rollback plan before being marked ready.

### 5. Visibility for Non-Technical Oversight
- No hidden changes — every feature or change must be visibly surfaced in the application's actual GUI; nothing lives only in code or backend logs.
- Every change ships with a plain-language change summary: what changed, why, and how to see/verify it in the UI, written for a non-developer audience.

### 6. Configuration-Driven Design Philosophy
- Business-level decisions should be configuration choices, not code choices — exposed as toggles, binaries, or option lists.
- Every application includes a web-based configuration console for managing these settings.
- Configuration changes committed via the console must apply at runtime, with zero downtime / no restart required.

### 7. Self-Service & Operator Recovery (B2B Philosophy)
- Diagnostics & health dashboard so operators can self-diagnose before filing a ticket.
- Self-service remediation actions for common failure modes (retry, reset, reindex, clear cache) exposed as buttons in the configuration console.
- Feature flags with safe defaults, so a misbehaving feature can be disabled by the operator without a code deploy.
- Actionable error messages that tell the operator what to do next, not raw stack traces.

## Non-Functional Requirements

### 8. Enterprise-Grade Non-Functional Requirements
- Resilience & self-healing: applications absorb failures and recover without human intervention where possible.
- Observability with proactive alerting: issues surface loudly and early — never fail silently. Unified telemetry (metrics, logs, traces) from day one; avoid fragmented tooling.
- Structured, consistent logging: logs must be parseable and standardized.
- Built-in reporting & analytics dashboards for health and usage, always visible without being requested.
- Security & compliance logging enabled by default.
- Role-based access control as a standing requirement in the configuration console.
- Performance & capacity monitoring with early-warning thresholds.
- Backward compatibility & safe upgrade paths — version upgrades must never break existing customer configurations or data.
- Multi-tenant isolation — one customer's load spike or issue must never affect another customer.

### 9. Continuous Security & Standards Compliance
- Scheduled dependency & vulnerability scanning for all third-party libraries.
- Auto-patch pathway for low-risk security fixes; flagged review queue for medium/high-risk fixes.
- Sena periodically benchmarks the architecture against current industry standards and flags drift, so improvement is both feature-driven and standards-driven.
- Security is treated as paramount — continuous checks-and-balances, not periodic audits only.

## Acceptance Criteria
- An ADR exists and is accepted codifying the separation, delivery-pipeline, and governance decisions implied by this requirement.
- Every application built under this model has: a sibling (never nested) Sena workspace, an isolated database schema, a running changelog, a living architecture document, and a repeatable extraction/shipping procedure.
- No change reaches "ready" status without passing the full change pipeline and receiving a risk-level tag; Medium/High risk changes carry explicit human review evidence.
- No production deployment occurs without a final human go-ahead recorded in the audit trail.
- Every application ships a configuration console exposing feature flags, RBAC, and self-service remediation actions, with runtime (no-restart) apply semantics.

## Summary Principle
Sena builds and evolves the application piece by piece, tested and regression-checked at every step, always visible in plain language and in the UI, always configurable without downtime, always recoverable by the operator, always secure, and always separable into a clean, shippable repository on demand.
